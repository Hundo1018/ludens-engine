# LudensEngine Benchmark Report

Generated by `pixi run benchmark`. Each table is a cross matrix produced
by running one identical workload across interchangeable implementations,
validating that LudensEngine's swap seams (ECS `StorageBackend`, collision
`BroadPhase`/`NarrowPhase`) are both correct (see the parity tests) and
performance-competitive. Timings are wall-clock ns via `perf_counter_ns`
with `keep()` guarding against dead-code elimination; absolute numbers are
machine-specific, so read the *relative* columns.

## Engine implementations — movement workload

Note the two archetype rows: `archetype (handle)` is the ergonomic
`query2 + get/set` path (allocates a List per query, walks the entity index
per access); `archetype (soa)` is the column path via `query2_views`. The SoA
row is ~10x faster than the handle row — the handle path, not ECS storage, is
what made the first version of this benchmark look slow.

## Foundation — rigid-transform representations (PGA motor vs dual quat vs mat4)

The same random rigid transforms applied and composed through each
representation (see `test_motor_parity` for the equivalence proof).

The second table prices the **Lie layer** (`geometry/galie.mojo`: exp / log /
geodesic on PGA motors) against the classical interpolation routes on the same
transforms. Read it with the semantic caveat: `geodesic3` produces a true SCREW
motion — rotation and translation share an axis and interpolate as one uniform
rigid motion — whereas `slerp + lerp` decouples them and traces a DIFFERENT
path, and a matrix cannot be interpolated at all without decomposing first
(a blend of two rigid matrices leaves SE(3)). So this table prices the
abstraction; it does not claim the routes are interchangeable. The dual-quat
row goes through the motor bridge because `DualQuat` has no native ScLERP —
it prices what the current API makes you pay, not the algorithm's floor.

## Physics — GPU XPBD cloth (CPU vs GPU scaling)

Gather-Jacobi PBD cloth, identical math on both sides (parity ~1e-6 in
`test_gpu_cloth`). GPU rows only appear on hosts with an accelerator.
(All GPU rollouts share ONE `DeviceContext`: creating several per process
hangs on this nightly — the per-call driver is why this section was empty
in earlier reports.)

The second table splits that end-to-end number into host->device upload,
device compute and device->host readback, and adds the shape a real game loop
has: draining positions back to the CPU EVERY frame. Rows are normalized per
simulation step, so the phases are additive. Read it as the answer to "is the
bus or the kernel the bottleneck?" — and note the answer is workload-dependent,
not a constant. With a single drain, transfers are ~10% of a 65k-particle
rollout: essentially free. Switch to per-frame readback and the bus becomes the
DOMINANT cost — at 65k the readback column alone runs ~2.5x the compute column,
and the rollout total grows ~3x. Against the CPU rows that is the difference
between a ~29x and a ~11x GPU win at 16k particles: **most of the GPU's
advantage on this workload is spent on getting the answer back**, which the
end-to-end rows alone cannot show.

Two second-order effects only the split makes visible: per-frame syncing costs
the compute column itself ~3-6% (it drains the launch pipeline, so kernel
dispatch stops overlapping), and readback cost grows SUBLINEARLY in particle
count while compute amortizes better — so the larger the cloth, the worse
readback looks *relative* to compute (~0.9x of compute at 4k, ~2.5x at 65k).

## Physics — island-parallel solver (serial vs worker threads)

Bit-identical by construction (islands share nothing, test_islands_par);
the honesty row shows the thread overhead when there is one big island.

The second table is the **core-scaling (Amdahl) curve**: the same scene with
the fan-out width pinned to 1..20 workers, min-of-3 per point. Worker count
changes only the schedule — `test_islands_par` gates that every width is
bit-identical to serial — so the curve compares one computation at different
widths, not different computations.

It does NOT scale linearly, and that is the useful result: throughput
saturates near **1.6x** and stops improving past ~4 workers on a 20-thread
host. Inverting Amdahl at that plateau puts the parallel fraction of
`step_soft` at only **~40%** — the other ~60% (broadphase, island labelling,
pose integration, sleep update, contact-cache management) is still serial, and
that serial remainder, not the thread pool, is what caps the solver. It is
also the concrete reason the scheduler seam only repays its threads at larger
N: there is simply not much parallel region to amortize them over.

Two further readings. `workers=1` is a few percent SLOWER than the serial
path here — the pure fan-out tax with no parallelism to win (on the finer
grained colored curve below the same tax falls inside run-to-run noise).
Note also that above ~4 workers the curve is FLAT, so which exact width comes
out best moves between runs (typically 6-12); read the plateau, not the
argmax. And the dip at `workers=8`
reproduces under min-of-3 in BOTH this curve and the colored one below, two
workloads with completely different task granularity, which makes it a
property of the host rather than of either workload. The likely mechanism
(untested here) is topology: this is a 6 P-core / 8 E-core part, so a width
of 8 has to place workers on E-cores or across hyperthread siblings while a
barrier waits on the slowest of them, whereas 12 maps onto the P-cores'
hyperthread set.

build", and that is NOT what these rows say: SAH also **builds ~1.7x faster**

build is the weak one*; a median split over a proper O(n log n) sort would

## Maturity assessment

- **Every comparable-method seam has a benchmark row.** The seam / parity-test /
  benchmark coverage matrix lives in `docs/CATEGORY.md` §2 (architecture law v2,
  2026-07-13): a seam variant ships with its parity test AND its report row.
- **Swappability holds end-to-end.** All five ECS backends (sparse, archetype,
  bitset, reactive, naive) plus the OOP engine produce identical results on the
  shared scenarios (`test_backend_parity`, `test_oop_engine`, `test_system_soa`),
  so the storage seam is mature: strategies swap with zero game-code change.
- **The scheduler seam swaps too.** Sequential, entity-actor and system-actor
  schedulers — under serial and parallel dispatch — all produce identical world
  state (`test_scheduler_parity`, across sparse and archetype backends). The
  benchmark shows the cost shape: the actor schedulers add mailbox build/route/
  drain overhead over the plain loop, and parallel dispatch only starts to repay
  its thread-launch overhead near N=4000 — below that the per-actor work is too
  small to amortize it. Determinism is preserved because each parallel round only
  mutates disjoint data and merges/routes serially.
- **ECS vs OOP is a crossover, not a winner.** The fast SoA/SIMD path is what
  makes ECS competitive — and it wins exactly where theory says it should:
    - W2 scattered selective-read over fat entities: `archetype (soa)` beats
      `oop-fat`, because the hot Position column stays cache-resident while the
      AoS object drags its cold payload through cache on every access.
    - W3 column integrate: `archetype (simd)` is fastest by far — contiguous
      columns vectorize; AoS objects do not.
    - W1 slim full-update (tiny components, touch everything): AoS/OOP stay
      competitive — there is no locality gap to exploit, so the paradigm with
      the least indirection wins.
    - W4 structural churn (add/remove components): `sparse`/`oop` beat
      `archetype`, which pays archetype relocation.
  The earlier 'OOP always wins' result was an artifact of measuring the ECS
  *handle* path on the *one* workload (W1-shaped) where AoS has no disadvantage.
- **Collision scales.** Quadtree/octree, spatial hash and BVH all pull away from
  brute force as N grows (its total time grows quadratically), and narrowphase
  cost ranks cheap→expensive (AABB ≈ circle < SDF < OBB < SAT < GJK+EPA);
  AABB/SAT/OBB/GJK agree on hit counts, confirming they detect the same overlaps.
- **The N ceiling is gone (was: `InlineArray[Int, cap]` by value).** The sparse
  index no longer has a fixed cap — `test_sparse_large` spawns **1,000,000**
  entities and checks counts and high-id component reads. The remaining
  `InlineArray` in `ecs/archetype.mojo` indexes archetype-graph edges by
  *component slot*, not by entity, so it does not bound N.
  What the tables above still under-show is the RAM-spill REGIME: the movement
  rows stop at N=65536, where a fat entity still reaches L3, so the W2 locality
  win reads as ~2x-4x. The memory-mountain probe in
  `ECS_VS_OOP_INVESTIGATION.md` §3 carries the workload past L3 (up to 4,194,304
  elements / 64 MB) and the gap widens as predicted — fat selective read goes
  SoA 0.44 vs AoS 1.82 ns/op (**4.1x**, still widening with N).
- **Hardware profiling backs the locality claim (four-way cross-validation).**
  The layout argument is not left as theory — `ECS_VS_OOP_INVESTIGATION.md` §5
  pins it with four independent instruments that agree:
    - `llvm-mca` (static): the AoS and SoA fat loops are IDENTICAL
      (4009 cycles / 1000 iter, IPC 1.00) — so arithmetic is not the difference.
    - `cachegrind` (deterministic, no prefetcher model): AoS fat read misses L1
      **100%** and last-level **83.8%**; SoA misses 12.5% / 0.5%. This is the
      no-prefetch upper bound.
    - `perf stat` (real PMCs, `paranoid=-1`, pinned to a P-core, N=65536x400):
      AoS sequential IPC 0.94 / L1-dcache miss 17.4% (**5.6x** slower than SoA);
      AoS SCATTERED — which defeats the stride prefetcher — falls to IPC 0.64 /
      30.9% miss (**8.3x**). SoA is nearly immune to scatter (0.026 -> 0.0275 s,
      +6%) because the 512 KB position column stays L2-resident.
    - the timing memory-mountain above.
  Alder Lake's stride prefetcher is what reconciles cachegrind's 84% predicted
  RAM misses with the measured 5.6x: it hides most of them while the access
  pattern stays linear, and stops helping the moment it does not.

_Conclusion: LudensEngine's seams are proven correct, and once ECS is measured
through its intended SoA/SIMD path it lands where its data-locality profile
predicts — beating OOP on selective/columnar/SIMD workloads while OOP stays
ahead on tiny touch-everything updates and structural churn._
