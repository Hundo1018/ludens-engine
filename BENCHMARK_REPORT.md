# LudensEngine Benchmark Report

Generated by `pixi run benchmark`. Each table is a cross matrix produced
by running one identical workload across interchangeable implementations,
validating that LudensEngine's swap seams (ECS `StorageBackend`, collision
`BroadPhase`/`NarrowPhase`) are both correct (see the parity tests) and
performance-competitive. Timings are wall-clock ns via `perf_counter_ns`
with `keep()` guarding against dead-code elimination; absolute numbers are
machine-specific, so read the *relative* columns.

## Collision algorithms

The narrowphase table includes the CGA rows: sphere-sphere answered by
conformal-algebra inner products vs the analytic euclidean test (parity in
`test_cga_narrowphase`) — the price of the GA abstraction, measured.

The final table settles the HETEROGENEOUS case, which is the one the
"unified branchless meet" argument is actually about: the claim is that one
algebraic incidence test beats a traditional dispatcher full of per-shape-pair
branches. Both paths hold spheres and planes in one registry over identical
candidate pairs; the control is a hand-written euclidean switch. Plane count
is the scaling axis, because it controls how often the dispatch changes
branch, and the planes are interleaved through the cloud rather than left in
one contiguous run (a run is trivially predicted and would flatter the branchy
path).

CGA loses at every mix, by **2.4x-3.2x**, and the ratio does not improve as
the scene gets more heterogeneous. Two reasons, and the first is the more
important one: `CgaShapeNarrowPhase` **still branches on shape kind**, exactly
like the euclidean dispatcher. The uniformity CGA buys is in the FORMULA
(a sphere-sphere and a sphere-plane test are both grade-1 inner products), not
in the dispatch — so there is no branch elimination to collect, and what
remains is the cost of carrying 32-float multivectors instead of 4 floats.
A genuinely branch-free version would need one uniform representation and one
code path for every pairing, which this algebra layer does not currently
provide.

Note the hit counts differ by ~0.3% between the two paths. That is a second
result rather than noise: the euclidean path measures the centre distance
directly, while CGA reconstructs it as d² = r₁²+r₂²−2·S₁·S₂ — a subtraction of
similar magnitudes — so a few pairs sitting exactly on the touching boundary
fall on the other side. The abstraction costs a little conditioning as well as
a little speed.

## Collision — 3D signed distance fields

The engine'\''s existing SDF layer is 2D, so this is a 3D layer rather than a
port of a working one — worth stating because the roadmap assumed otherwise.
Contact is found by driving the two fields to a common value, and the
quantity that IS the penetration is the SUM of the fields where they agree,
not the minimum of their maximum: for two spheres that minimum is half the
overlap, because the balance point splits the gap. `test_sdf3` pins the
converged answer against the analytic sphere pair — 115/115 on hit
classification and ~1e-7 on depth.

Against a closed form the SDF is **~20x slower**, which is the price of
finding a contact rather than deriving it. Note the iteration cap barely
matters (8, 16 and 32 all land at ~94 ns): for unit-gradient primitive fields
the descent closes the gap in one step and exits early, so the cap only binds
on CSG fields, which are a bound on distance rather than the distance.

The CSG row has no analytic row beside it, and that absence is the result. A
box with a sphere bitten out of it is answered by the same code path at ~4x
the primitive cost, where the analytic narrowphase cannot express the shape
at all. Contact cost also stops depending on tessellation, since there is no
mesh in between.

Still to do: this lives at narrowphase level and is NOT yet wired into
`solver6`, which dispatches on a box/sphere/capsule kind tag and needs a
multi-point manifold rather than a single deepest contact.

## Foundation — rigid-transform representations (PGA motor vs dual quat vs mat4)

The same random rigid transforms applied and composed through each
representation (see `test_motor_parity` for the equivalence proof).

The second table prices the **Lie layer** (`geometry/galie.mojo`: exp / log /
geodesic on PGA motors) against the classical interpolation routes on the same
transforms. Read it with the semantic caveat: `geodesic3` produces a true SCREW
motion — rotation and translation share an axis and interpolate as one uniform
rigid motion — whereas `slerp + lerp` decouples them and traces a DIFFERENT
path, and a matrix cannot be interpolated at all without decomposing first
(a blend of two rigid matrices leaves SE(3)). So this table prices the
abstraction; it does not claim the routes are interchangeable. The dual-quat
row goes through the motor bridge because `DualQuat` has no native ScLERP —
it prices what the current API makes you pay, not the algorithm's floor.

The chain table is the compact representations'\'' predicted advantage regime.
The per-point APPLY rows above are the matrix'\''s: one dot product per row,
nothing to beat. Composition is the other side — a motor and a dual quat are
8 floats against a matrix'\''s 16, so a long chain streams half the memory.
Sweeping chain length K separates the two regimes instead of letting the
apply rows stand for both.

The gap closes monotonically: at K=4 mat4 leads by ~1.45x, at K=64 by ~1.13x,
and by K=256 the **dual quaternion overtakes it**. The
crossover is real but the margin is small, so the honest reading is that the
8-float representations are competitive on long chains and behind on short
ones — not that they are the better choice outright. The PGA motor stays
slightly behind its dual-quat twin throughout, which is consistent with the
apply rows: same 8 floats, more expensive product.

The next table covers what the CONFORMAL algebra adds over the rigid one:
uniform scale as a versor, and spherical INVERSION. Inversion is the only
transform in the engine with no 4x4-matrix counterpart — it is conformal but
not affine, so it is not a linear map on homogeneous coordinates at all — and
it falls out of the SAME sandwich as plane reflection with a dual sphere
substituted for a dual plane. `test_cga_inversion` gates it against the closed
form and against the structural properties (involution, the sphere fixed
pointwise, inside/outside exchanged) to ~1e-6.

The same table answers the point-to-arc question. A circle IS a first-class
object in this algebra (a grade-2 round, carried here as its sphere/plane
pair), and both scalars the distance needs come back as inner products with no
coordinate case analysis: the signed plane distance is up(p)·π and the radial
term falls out of up(p)·S. But the SPLIT into normal and radial components and
their Pythagorean recombination is the same step the euclidean routine takes —
the algebra replaces two dot products, not the algorithm. Measured at ~6x the
closed form (`test_cga_circle` gates parity to ~5e-6, including a point on the
axis where the closest point is not unique, and a point exactly on the circle
where the subtraction under the root can go negative).

The last table turns the CAPABILITY claim into a measurement instead of an
assertion. A 4x4 matrix cannot absorb an inversion at all, so a matrix
pipeline has to BREAK a mixed chain at every inversion: fold the affine run
into a matrix, transform, apply a closed-form inversion, start a new matrix.
A versor absorbs all of it, so inversion COUNT is the scaling axis.

The shape is exactly what the claim predicts: **the versor is flat in the
inversion count** (~280-290 ns whether the chain holds 0 inversions or 8 —
one folded operator, one pass per point), while the matrix path grows
linearly at ~7.3 ns per inversion (0.97 -> 4.70 -> 23.5 -> 59.6 ns).

It still does not pay. Extrapolating the two lines puts the crossover near
**39 inversions in a single chain**, which no realistic pipeline has. So the
honest summary is that the capability is real and now measured — the versor
genuinely does what the matrix cannot, at a cost that is independent of how
much of it you use — but the 32-component generic multivector makes the
constant so large that the structural advantage never becomes a time
advantage. A specialised conformal versor, in the way `Motor3` specialises
the PGA even subalgebra, is what would move that constant.

One implementation note that the parity suite earned: the rotor'\''s bivector
had a sign error in its y term (mask 4|1 yields the CANONICAL blade e1e3,
which is -e3e1). Every GA-only check passed anyway, because both sides of a
GA-vs-GA comparison carried the same convention. Only the cross-check against
an independent matrix implementation exposed it.

The cost is the story: with versors hoisted out of the loop, the conformal
sandwich runs **~200x** the hand-written closed form for both operations.
So "matrices cannot express inversion" must not be read as "you need CGA for
inversion" — the closed form is three lines and 1.5 ns. What the versor buys
is COMPOSABILITY: scale, rotation, translation and inversion multiply into one
operator that the conformal group is closed under, and `D(a)·D(b) = D(ab)` is
checked as part of the parity suite. That is an expressiveness argument, and
on this evidence it is not a performance one.

## Collision — LBVH build: CPU radix sort vs GPU bitonic sort

An earlier revision of this section reported the device losing at every N and
blamed the bitonic sort'\''s worse complexity. **That conclusion was wrong**, and
the way it was wrong is worth recording: it came from comparing FULL BUILDS,
where both sides share a hierarchy emit that dominates the total, and from two
measurement defects that the shared tail hid.

- The GPU path fed its device-produced Z-order into `build(lbvh=True)`, which
  re-runs the whole host Morton+radix sort. That is idempotent, so the result
  was correct and the row silently charged the GPU path for a CPU sort it
  never needed. `build_lbvh_presorted` now emits from a given order.
- The emit itself recomputed each node'\''s box by rescanning its whole leaf
  range, making it O(n log n) AABB merges for a value the two children
  already hold. Bottom-up bounds made **every** BVH build ~1.7x faster.

With both fixed, and with the sort measured on its own rather than inferred
from totals, the answer reverses: **the device sort wins from ~16k leaves and
by roughly 3x at 65k**, and the full build crosses over too — CPU ahead below
~16k, GPU ahead at 65k. Bitonic'\''s O(n log²n) and its
~136 kernel launches at that size are simply not enough to give the advantage
back.

What stands from the earlier reading is the reason bitonic was chosen at all:
an LSD radix sort must be STABLE, the natural GPU scatter claims slots with a
per-bin atomic in warp-arrival order, and an unstable radix sort is silently
WRONG rather than slow. A stable GPU radix (per-block histograms plus a global
scan) would widen the margin further; it is no longer the difference between
winning and losing.

## Collision — batched GPU raycast vs the CPU BVH

The query-side counterpart to the GPU broadphase, and the one place in this
report where the device wins outright. The BVH answers a ray in O(log n) by
descending only the nodes it enters; the kernel answers it in O(n) by testing
every box, but with one ray per lane. Ray count is the axis, since both sides
amortise a fixed cost over it — a tree build on one side, host<->device
transfer on the other.

**The GPU is 7.5x-9.2x faster at every ray count tested**, including 256 rays.
Parity is exact rather than statistical: same proxy per ray and bit-identical
distances (`test_gpu_raycast` compares proxy ids, because two boxes at nearly
the same distance are exactly where a differing tie-break would hide behind a
distance-only check). Unlike the broadphase kernel this one is fully
deterministic — each thread keeps its nearest hit in registers and writes
once, so there is no atomic and no ordering question.

One caveat that decides how to read the low-ray rows: the CPU row INCLUDES the
BVH build, which is right for a scene rebuilt each frame but wrong for a
static level whose tree is built once and reused. Strip the build and the CPU
cost at 65536 rays falls to roughly 770 ns/ray — still ~6x the GPU, so the win
survives the correction at high ray counts, but the 8x at 256 rays is mostly
the build and would largely disappear against a persistent tree.

## Collision — GPU all-pairs broadphase vs the CPU structures

Every CPU broadphase here wins by doing FEWER tests. This one keeps the O(n²)
enumeration and throws lanes at it instead (`collision/bp_gpu.mojo`: one
thread per box walking j > i, hits appended through an atomic cursor). Pair
sets are identical to brute force — `test_gpu_broadphase` gates that on a
sparse and a dense scene, plus an undersized output buffer that must REPORT
overflow rather than truncate silently.

The shape is the result: GPU cost is **nearly flat in N** (~3.4 -> ~5.7 ms
from 512 to 8192 boxes, absorbing 256x the pair tests for 1.7x the time)
while CPU brute force grows quadratically (0.16 -> 43.8 ms). So the device
overtakes every O(n²) CPU path somewhere between 512 and 2048 boxes, and by
8192 it is ~7.6x faster than CPU brute and ~5.7x faster than SAP.

The trend lines cross. The grid is ahead at 8192 (by 1.27x), and by **32768
the device wins ~1.7x** (14.1 ms vs 24.1 ms) — while also emitting 4,892 exact
pairs against the grid'\''s 38,845, an **8x superset**. So above roughly 16k
boxes the GPU is both faster and tighter. One caveat still applies to the
smaller rows: the grid emits a larger, conservative candidate set
(9476 vs 1235 pairs at N=8192), so its row is not equal work — the same
not-apples-to-apples caveat the main broadphase table carries. And the GPU
row is END-TO-END: it includes uploading boxes and reading pairs back, which
is ~3.4 ms of fixed cost that dominates entirely below ~2k boxes. A pipeline
keeping boxes device-resident would pay much less of it.

One structural limitation, stated because it decides where this can be used:
the atomic cursor makes the output ORDER nondeterministic. `solver6` depends
on a deterministic pair order for bit-identical results, so this cannot go
behind that seam without sorting first. It also does not implement the
`BroadPhase` trait at all — the trait has nowhere to carry a device context,
and one context per instance is the pattern that hangs on this nightly.

## Collision — sweep-and-prune vs the other broadphases, by motion speed

SAP (`collision/bp_sap.mojo`) keeps last frame's sorted endpoint order and
repairs it with an insertion sort, so its cost depends on TEMPORAL COHERENCE
rather than on N alone. The sweep axis is therefore how far bodies move per
frame, not how many there are. Pair sets match brute force exactly
(`test_sap`, including across moving frames, a teleport and a population
change), so this table is cost-only.

The scene oscillates with FIXED amplitude, so the overlap count stays ~90-110
pairs at every speed and the rows compare equal work — a sweep that let boxes
drift apart at high speed would be changing density, not coherence.

Three readings, one of them uncomfortable:

- **SAP delivers on its premise**: ~3x cheaper under jitter than under real
  motion, which is the insertion sort finding the order nearly correct.
- **SAP beats the DBVH here at every speed**, by 3-4x. That is not a
  contradiction of the persistent-vs-rebuild table above: the DBVH's advantage
  is bounded by its FAT MARGIN, and that table jitters inside it. Here motion
  is sustained, so leaves escape their fat boxes continuously and the tree
  pays reinsertion every frame. The lesson is that "temporal coherence" is not
  one property: a margin-based structure needs motion below a THRESHOLD, while
  a sort-based one only needs few INVERSIONS, and sustained slow drift
  satisfies the second while violating the first.
- The spatial hash wins outright at every speed ON THIS SCENE, and is
  flat across the coherence axis because it rebuilds from scratch in O(n) and
  has no state to invalidate.

That last row held only because every box in that scene is the same size,
which is the grid'\''s best case. The second table sweeps OBJECT-SIZE SPREAD,
the hash'\''s documented weak point: a hash has one cell size and no single
choice suits a wide spread — big boxes are duplicated into many cells while
small ones leave most cells nearly empty. Two grid rows are run per mix, one
cell sized for the small boxes and one for the large, so the result cannot be
dismissed as a badly tuned grid.

**At a 20:1 spread SAP wins outright**: ~27 ms against ~64 ms for the
best-tuned grid and ~440 ms for the small-tuned one, a 16x gap — and it wins
on the OTHER
axis too, emitting 147,969 exact pairs where that grid emits 732,550, a 5x
superset whose surplus the narrowphase then has to reject. A sorted sweep has
no cell size to get wrong. So the grid is the right default for uniformly
sized worlds and the wrong one as soon as scale varies, which is a sharper
statement than either structure simply being faster.

## Physics — GPU XPBD cloth (CPU vs GPU scaling)

Gather-Jacobi PBD cloth, identical math on both sides (parity ~1e-6 in
`test_gpu_cloth`). GPU rows only appear on hosts with an accelerator.
(All GPU rollouts share ONE `DeviceContext`: creating several per process
hangs on this nightly — the per-call driver is why this section was empty
in earlier reports.)

The second table splits that end-to-end number into host->device upload,
device compute and device->host readback, and adds the shape a real game loop
has: draining positions back to the CPU EVERY frame. Rows are normalized per
simulation step, so the phases are additive. Read it as the answer to "is the
bus or the kernel the bottleneck?" — and note the answer is workload-dependent,
not a constant. With a single drain, transfers are ~10% of a 65k-particle
rollout: essentially free. Switch to per-frame readback and the bus becomes the
DOMINANT cost — at 65k the readback column alone runs ~2.5x the compute column,
and the rollout total grows ~3x. Against the CPU rows that is the difference
between a ~29x and a ~11x GPU win at 16k particles: **most of the GPU's
advantage on this workload is spent on getting the answer back**, which the
end-to-end rows alone cannot show.

Two second-order effects only the split makes visible: per-frame syncing costs
the compute column itself ~3-6% (it drains the launch pipeline, so kernel
dispatch stops overlapping), and readback cost grows SUBLINEARLY in particle
count while compute amortizes better — so the larger the cloth, the worse
readback looks *relative* to compute (~0.9x of compute at 4k, ~2.5x at 65k).

## Geometry — DCGA spike: quartic surfaces as a linear incidence test

The torus was raised as a gap in the CGA coverage. It is not one: a torus is
a QUARTIC, `Cl(4,1)` represents only quadrics and lower, so "torus
intersection via CGA" is a category error rather than a missing feature.
Double CGA (`Cl(8,2)`) is the algebra that does cover it, by tensoring two
conformal copies so products of the two points supply degree-4 monomials.

**The dense algebra is out of reach on this toolchain, and measurably so.**
`Multivector[p,q,r]` unrolls the geometric product fully at compile time, so
cost grows with the SQUARE of the blade count. Measured for one product:
32 blades 4 s, 64 2 s, 128 8 s, 256 30 s, 512 exceeds a 6 GB address-space
cap, and `Cl(8,2)`'\''s 1024 blades — about a million term products — was killed
by the OOM killer outright. That is a structural wall, not a tuning problem,
and it is the reason the spike is written as the T-space subalgebra instead.

What that subalgebra is: the tensor product of two conformal points spans 15
distinct monomials (s², s·x, s·y, s·z, x², y², z², xy, yz, zx, s, x, y, z, 1
with s = x²+y²+z²), and every Darboux cyclide — planes, spheres, cyclides and
the torus — is a fixed coefficient vector over that basis. So incidence
collapses to a 15-term dot product, and `test_dcga` shows one call answering
all three surface types with nothing changed but the coefficients.

The cost is the notable part. DCGA runs a **flat ~3.87 ns regardless of
surface** — that flatness IS the uniformity — against 2.05-2.36 ns for the
hand-written tests, so **1.6x-1.9x**. Set that against the other GA rows in
this report: CGA sphere narrowphase costs 3.7x its analytic twin, and the
conformal VERSOR paths cost ~200x. The difference is not the algebra, it is
where the algebra is spent — used to DERIVE a representation it is nearly
free, carried as a runtime multivector it is not. The torus row is the
narrowest gap (1.64x) precisely because the hand-written torus needs a square
root and the DCGA form does not.

## Physics — MLS-MPM (material point method)

MPM sits between the engine'\''s other deformables. FEM keeps a fixed mesh and
therefore a fixed topology; PBF and SPH keep no rest shape at all. MPM carries
elastic state on PARTICLES and uses a background grid, thrown away each step,
only to resolve the coupling — so the material can flow, pile up and merge
while still remembering strain. That is the combination snow, mud and plastic
flow need, and it is the one class of material the other two solvers here
structurally cannot represent.

Plasticity is a determinant clamp on the deformation gradient: strain past a
yield range is FORGOTTEN rather than stored, which is precisely what turns an
elastic solid into a material that keeps a new shape. The benchmark shows it
costs **~0.5%** — it is a clamp and a rescale — and `test_mpm` shows what that
0.5% buys by running the identical dropped column both ways: the elastic body
springs back to height 0.64 after impact, the plastic one stays at 0.28.

Per-particle cost FALLS as the particle count grows (2693 -> 1300 ns) because
the grid is cleared every step regardless of how many particles occupy it, so
a 32³ grid'\''s fixed cost dominates at small counts and amortises away at
larger ones. Read the small-N rows as grid overhead, not as scaling.

## Physics — co-rotational tetrahedral FEM

A continuum next to the engine'\''s mass-spring lattice. `softbody.mojo` joins
particles with distance constraints, so its stiffness and volume response are
properties of how the lattice happens to be wired. FEM discretises the
material instead: each tetrahedron carries a deformation gradient and stress
comes from a constitutive law with real Lame parameters, so those become
material properties. `test_fem` measures the consequence — a pinned
cantilever under gravity holds volume to **0.04%** of rest.

The table prices the CO-ROTATIONAL part specifically, because that is the
trade that decides whether the method is usable. Linear elasticity measures
strain from displacement and is therefore only valid for small DISPLACEMENTS:
rotate an undeformed body and it reports enormous spurious strain. The
`linear (R=I)` rows are that control, run on the same meshes.

Extracting the rotation by polar decomposition costs **~5.6x** (roughly 710 vs
127 ns per tet, flat in mesh size for both since tets are independent). What
it buys is in the error column: after a 63-degree rigid rotation of an
UNDEFORMED body, the linear variant reports a peak spurious force of **83.6**
— which would tear the body apart — while the co-rotational one reports
**0.00**. That is not an accuracy improvement, it is the difference between a
method that works under motion and one that does not, and 5.6x is what it
costs.

## Physics — SPH vs PBF: explicit pressure against density projection

Both solvers run on the SAME particle state, grid and kernels, so this
isolates the one thing that differs: SPH turns density error into a pressure
FORCE and integrates it explicitly; PBF treats density error as a CONSTRAINT
and projects positions. The metric is cost per SECOND OF SIMULATED TIME, not
per step — per-step cost flatters whichever solver takes smaller steps, and
how large a step each survives is the entire practical question. Each row
carries the settled density and peak speed it reached, so a row that is cheap
because it diverged is marked as such rather than looking like a win.

The timestep story comes out as expected: **SPH is CFL-limited and PBF is
not**. SPH is stable to dt=1/120 and fails at 1/60 (density 1.76x rest, peak
speed 21 vs 0.12); PBF runs stably at 1/30, a 4x larger step.

The COST story does not. Despite needing a 4x smaller timestep, **SPH is
cheaper per simulated second** — ~22 ms against PBF'\''s ~26 ms at its largest
stable step, and ~1.9x cheaper than PBF at matched density accuracy (~22 ms vs
~43 ms). The reason is per-step cost: an SPH step makes two neighbour passes
(density, then forces) while a PBF step makes two PER ITERATION, so four
iterations cost about four times as much and exactly cancel the four-times
larger step.

So the usual framing — PBF is faster because it takes big steps — is not what
this measures. Two honest caveats on how far to carry that. The scene is a
gentle settling column at 216 particles on CPU, and SPH'\''s stable step shrinks
with fluid stiffness and with the velocity field, so a violent or stiffer
scene pushes SPH down while PBF holds — the crossover is a property of how
hard the CFL limit bites, not a constant. And PBF'\''s neighbour lists are built
once per step and reused across iterations here (the standard arrangement);
rebuilding them per iteration, which an earlier revision did, cost ~7% more
for identical settled density.

## Physics — Position-Based Fluids

The engine'\''s first fluid, and it is deliberately the SAME solver shape as the
XPBD cloth already here: predict positions, project a constraint, derive
velocity from the position change. Cloth projects a distance constraint, PBF
projects a DENSITY one (C_i = rho_i/rho_0 - 1), so the machinery is shared and
only the constraint changes — which is what made this the cheapest entry into
fluids rather than a parallel body of code.

Rows are read like the cloth ones: cost next to the error it bought, here mean
density relative to rest (1.00 = incompressible). Every iteration count lands
within ~2% of rest and cost is linear in iterations; per-particle cost is
roughly flat as N grows, which is the uniform grid keeping neighbour search
near-linear.

Three things had to be right, and each was caught by a physical gate rather
than by inspection — worth recording because each produced a plausible-looking
fluid that was wrong:

- **Rest density must be CALIBRATED to the particle spacing, not chosen.** With
  rho_0 above what the sampling can reach, every particle reads as under-dense,
  the correction pushes outward everywhere, and the fluid explodes against the
  container. It is now computed from a lattice sum at the seeding spacing.
- **XSPH viscosity must be normalised by density.** The poly6 kernel here is
  unnormalised and of order 1e3, so summing it raw over ~30 neighbours injected
  velocity thousands of times larger than the field it smooths, and the solver
  GAINED energy every step. The dam-break energy gate is what caught it.
- **The per-iteration displacement needs a cap.** Without one the projection
  overshoots far enough to push particles past each other, and behaviour was
  erratic in the ITERATION COUNT — 2 and 4 converged, 3 and 6 collapsed to ~16x
  rest density. Erratic in the iteration count is the signature of divergence,
  not of under-resolution, and `test_pbf` now asserts convergence at every
  count rather than at one.

## Physics — cloth solver seam (XPBD vs VBD, cost at a quality level)

Vertex block descent (`physics/vbd_cloth.mojo`, arXiv:2403.06321): per-vertex
3x3 Newton steps swept over a checkerboard 2-coloring (edges are bichromatic,
so a color updates in parallel with no atomics — same determinism scheme as the
XPBD gather-Jacobi). Every row carries the worst edge-stretch error it bought,
so cost is read AT a quality level (physical gates + CPU/GPU parity in
`test_vbd_cloth`).

The second table sweeps the TIMESTEP at fixed iterations, which is where
VBD's headline property — an implicit solve that is unconditionally stable —
is supposed to pay off. Stiffness is deliberately not the axis: XPBD's
distance projection is already maximally stiff by construction (it snaps
edges toward rest length), so there is no stiffness knob on that side to turn.

The result does not favour VBD. It never blows up — error stays bounded at
every timestep, which is the stability claim in its weak form — but at a fixed
5 iterations its worst edge stretch grows from ~0% at dt=1/120 to ~48% at
dt=1/8, while XPBD holds ~0% throughout and costs ~3x less per step.

That comparison has a bias which has to be stated: the error metric is worst
EDGE STRETCH, and edge stretch is exactly the quantity XPBD projects onto, so
the metric measures XPBD's own invariant. VBD instead minimises an elastic
energy at finite stiffness, and with the iteration count held fixed it simply
does not converge far enough as dt grows.

The third table removes that bias by measuring the cloth'\''s SHAPE — how far
the sheet has sagged — which neither solver is built to optimise, against
each solver'\''s own 200-iteration answer. It changes the picture. XPBD'\''s
effective stiffness depends on how many projection sweeps it got, so at low
iteration counts its cloth is far too soft: at 10 iterations it has reached
**0%** of its converged shape while VBD is at **34%**, and at 20 it is 30%
against VBD'\''s 61%. **VBD converges 2-3x faster per iteration**, which the
edge-stretch metric could not show at all.

Priced, though, that advantage does not survive: a VBD iteration costs ~3x an
XPBD one, so at matched shape fidelity XPBD is still ~1.7x cheaper (65% of
converged for 694 us against VBD'\''s 61% for 1,169 us). The precise statement
is therefore that **VBD wins the iteration count and loses the iteration
price** — which is a different and more useful claim than having no advantage
regime at all. Worth noting the two converge to nearly the same sag (1.136 vs
1.130), so they do discretise the same material and the comparison is fair.

## Differentiable simulation — gradient cost & Field abstraction

The `Field` seam (`RealF`/`DualReal`/`DualBatch`/`RevReal` tape, gradient
correctness in `test_diffsim`/`test_gmv_ad`): what a gradient costs via finite
differences vs forward-mode AD vs the reverse-mode tape, and what the
coefficient-generic `GMV` multivector costs vs the specialized `Motor3`
sandwich. Read the two rollout tables together: on this few-flops-per-step toy
the tape's recording overhead dominates (~19x a plain step), but its cost is
FLAT in the parameter count.

The sweep table MEASURES that claim instead of extrapolating it. Primal work is
held constant (NP x BURST = 2000 steps in every row), so the only variable is
how each method's overhead scales with the parameter count:

- **Reverse tape is flat, confirmed**: NP 8 -> 200 (a 25x range) moves it only
  35.9 -> 39.7 ns/op (+10.6%).
- **Forward differences and DualBatch are linear**, as their rollout counts
  imply (N+1 and ceil(N/4) rollouts); DualBatch holds a constant ~2.86 ns per
  4-lane chunk across the whole sweep.
- **The emitted adjoint changes the picture entirely.** `adjoint s2s` is the
  routine a Taichi / Dr.Jit-class source-to-source tool emits — the step
  function differentiated once and written out as an explicit backward pass,
  with no node list and no indirection. It is **flat in the parameter count**
  like the tape (3.9 -> 4.9 ns/op over a 25x range) and simultaneously **~9x
  faster than the tape**, beating every other method at every NP tested,
  including DualBatch at NP=8 where forward mode should be at its strongest.
- Against the primal rollout (0.87 ns/step) that is **~4.5x**, versus the
  runtime tape's **~40x**. Reverse-mode theory puts the floor near 2-4x the
  primal, so the emitted adjoint lands close to it and the tape's overhead is
  shown to be almost entirely bookkeeping rather than gradient arithmetic.
- One structural correction to the usual claim, which the implementation makes
  unavoidable: source-to-source does NOT eliminate the tape, it shrinks it.
  The ground penalty is a branch on the primal state, so the backward pass
  still has to know which side each step took. But that checkpoint is ONE BIT
  per step instead of a node per operation — roughly two orders of magnitude
  less memory here — which is the real difference, and `test_adjoint` gates
  the replay against both the runtime tape and central differences precisely
  because an off-by-one in that recording would still look plausible.
- **Measured crossovers**: the tape overtakes finite differences at **NP ~ 12-15**
  and overtakes DualBatch at **NP ~ 45-50**. An earlier revision of this report
  extrapolated the DualBatch crossover from two points and put it near ~76; the
  measured value is ~1.5x lower, so that estimate is superseded by these rows.
  Both crossovers move earlier the heavier the per-step primal math.

## Physics — actuators (transmission, force generation, internal dynamics)

`Chain.step` took a torque vector, so every control loop lived outside the
engine and the engine knew nothing about what drove it. An actuator splits
that three ways — where the force lands, how much of it, and what lag sits
between command and force — because each varies independently.

The force law is AFFINE, which is why a motor, a position servo and a
velocity servo are one struct rather than three code paths: they differ only
in which coefficient is non-zero. `test_actuator` checks the position servo
against a hand-written PD loop step for step and finds 6e-8 divergence — the
abstraction is meant to be a repackaging, and a check that it merely
"converges to the target" would pass for any controller at all.

Cost is the first table and it is essentially zero: a bank of position
actuators tracks a bare torque vector within noise at every chain length,
which is the precondition for the abstraction being worth having.

The second table is the regime that justifies internal dynamics. A direct PD
servo must be stable at the caller'\''s timestep, and its stability limit falls
as gain rises. At dt = 1/240 the direct servo holds to kp = 500 and
**DIVERGES at kp = 2000**, while the same law driven through a first-order
actuator stays on target at kp = 8000. That is the trade in one line: the lag
costs response time and buys a usable gain range four times wider.

The filter is also exact in dt — 1 - exp(-t/tau) rather than the naive
`state += (u - state) * dt/tau` — so halving the timestep reproduces the same
trajectory instead of a different one. That error is invisible at any single
dt, which is why the test compares two.

## Physics — reduced-coordinate contact (articulated bodies that can touch)

Until this landed the two halves of the engine could not meet: `Chain`
integrates in joint space, `ContactScene6` resolves contacts in maximal
coordinates, and nothing connected them — an articulated body could not touch
anything. The bridge is the point Jacobian, which maps joint velocities to one
material point'\''s velocity and whose transpose maps an impulse there back to
joint torques, so a contact is solved without leaving generalised coordinates.

Cost scales with the ARTICULATED SYSTEM, not with the contact pair: every
impulse needs `J H⁻¹ Jᵀ`, so a Jacobian, the CRBA mass matrix and a dense
solve. That is the axis these rows sweep. The contact pass runs ~1.7-14x the
bare dynamics step depending on link count, most expensive at SHORT chains
where the step itself is nearly free and the fixed per-contact work dominates.

Two implementation notes the measurement forced. H depends only on q, which
does not change during a velocity iteration, so hoisting it out of the
contact loop cut the 2-link case by 1.7x — it had been recomputing an O(n³)
solve per contact per iteration. What remains is one dense solve per impulse;
factorising H once and reusing the factorisation is the next step and is not
done here.

And the contact is SPLIT into a velocity pass and a positional one. Folding
the penetration correction into the velocity target as a Baumgarte bias is
the obvious formulation and it pumps energy — the positional term is not a
physical impulse, so what it adds to the velocity stays there and returns as
speed on the next bounce. Measured at nearly 3x the free-swinging peak before
the split, and below it after (`test_chain_contact` gates exactly that).

## Physics — articulated chain: reduced (CRBA+RNEA) vs maximal coordinates

The same n-link pendulum chain in both formulations (physics parity via the
shared analytic period, test_chain): what exact reduced coordinates cost vs
soft maximal-coordinate joints as the chain grows.

The second table separates INVERSE from forward dynamics. Forward dynamics
forms the CRBA mass matrix and solves it densely; inverse dynamics recovers
the torques with one O(n) Newton-Euler sweep and no matrix at all. Both go
through the same `_rnea` routine — with zero acceleration it is the bias
term forward dynamics subtracts, with a real one it IS inverse dynamics —
which is what makes `test_inverse_dynamics`'\''s round trip meaningful: tau ->
qdd -> tau agrees to ~1e-6 across chains, a branching tree and a forest.

The gap widens with link count exactly as the complexity difference predicts:
2.3x at 2 links, 3.0x at 8, 5.2x at 24, **17.6x at 64**. That ratio is why a
controller computes feed-forward torque by inverse dynamics rather than by
solving forward dynamics backwards.

The joint-kind table exists to show a design claim holds: a prismatic joint
differs from a revolute one ONLY in its motion subspace — S is (axis, 0) for
one and (0, axis) for the other — so every sweep picks a half and nothing
else changes. A mixed chain therefore tracks a revolute one, which it does
(slightly faster, since a prismatic joint has no rotation to compose).

The limit rows price the one-sided constraint pass at ~1-3% while nothing is
against a stop, because the pass counts violations first and returns
immediately when there are none. Limits are solved as impulses rather than by
clamping q: clamping leaves the velocity pointing into the stop, so the joint
re-violates every step and jitters, and it moves the joint without a
corresponding impulse, which injects energy. `test_joints_lib` gates the
difference by requiring the joint to STAY on the stop under a driving torque
for 960 steps, not merely to be inside range once.

## Physics — island-parallel solver (serial vs worker threads)

Bit-identical by construction (islands share nothing, test_islands_par);
the honesty row shows the thread overhead when there is one big island.

The second table is the **core-scaling (Amdahl) curve**: the same scene with
the fan-out width pinned to 1..20 workers, min-of-3 per point. Worker count
changes only the schedule — `test_islands_par` gates that every width is
bit-identical to serial — so the curve compares one computation at different
widths, not different computations.

It does NOT scale linearly, and that is the useful result: throughput
saturates near **1.6x** and stops improving past ~4 workers on a 20-thread
host. Inverting Amdahl at that plateau puts the parallel fraction of
`step_soft` at only **~40%** — the other ~60% (broadphase, island labelling,
pose integration, sleep update, contact-cache management) is still serial, and
that serial remainder, not the thread pool, is what caps the solver. It is
also the concrete reason the scheduler seam only repays its threads at larger
N: there is simply not much parallel region to amortize them over.

Two further readings. `workers=1` is a few percent SLOWER than the serial
path here — the pure fan-out tax with no parallelism to win (on the finer
grained colored curve below the same tax falls inside run-to-run noise).
Note also that above ~4 workers the curve is FLAT, so which exact width comes
out best moves between runs (typically 6-12); read the plateau, not the
argmax. And the dip at `workers=8`
reproduces under min-of-3 in BOTH this curve and the colored one below, two
workloads with completely different task granularity, which makes it a
property of the host rather than of either workload. The likely mechanism
(untested here) is topology: this is a 6 P-core / 8 E-core part, so a width
of 8 has to place workers on E-cores or across hyperthread siblings while a
barrier waits on the slowest of them, whereas 12 maps onto the P-cores'
hyperthread set.

## Collision — BVH build heuristic (median-split vs binned SAH)

`test_sah` proves the two builds answer every query identically. Binned SAH
cuts a TIGHTER tree (lower Σ node area: 0.67x of median on the clustered
scene, 0.89x on the uniform one) and that shows up in cheaper raycasts —
1.35x on clustered, 1.14x on uniform, the smaller gain being the honest
result when a uniform scene leaves the two trees near-identical.

LBVH is the third row family: sort leaves by Morton code, split at the
highest differing bit. Its split decisions fall out of the sort instead of
being searched for, which is what makes it the standard construction to
parallelise. Here it **builds ~10x faster than median and ~6x faster than
SAH**, and its tree lands BETWEEN the two on tightness — so it dominates the
median build outright (cheaper to build, no slower to query) and trades
against SAH on a clean crossover: SAH repays its pricier build after roughly
**40k rays** on these scenes. Below that ratio — a tree thrown away every
frame, which is exactly the broadphase case — LBVH is the right choice; above
it, SAH is. Parity for all three builds is in `test_lbvh` (including
duplicate Morton codes, where no bit differs and the descent must fall back
to a median split, and a flat sheet with zero extent on one axis).

The textbook framing of this trade is "SAH buys query speed with a slower
build", and that is NOT what these rows say: SAH also **builds ~1.7x faster**
than median-split here. That is a property of this implementation, not of the
heuristic — the median path sorts centroids with an insertion sort (O(n²)),
while binned SAH only histograms into 12 bins per axis (O(n)). So the honest
reading is that SAH dominates on both axes *because the median baseline's
build is the weak one*; a median split over a proper O(n log n) sort would
close the build gap and restore the classical trade-off.

## ECS — chunked (paged) columns vs one growable column

`ChunkedBackend` is `NaiveBackend` with exactly one thing changed: a column
is a list of fixed 1024-row pages instead of a single growable `List`.
Dense id indexing, the Optional cell, the generational lifecycle and the query
shape are all identical, so the naive-vs-chunked pair isolates the storage
layout and nothing else. Both run the full parity suite
(`test_backend_parity`, `test_iter_parity`).

The result is negative for chunking on every axis measured: ~2x slower to
grow, ~1.8x slower to iterate, ~2.5x slower under churn. The structural claim
does hold — page count is bounded by N/1024 by construction (118 pages for
60k entities across two columns) and no existing row is ever copied — but it
does not convert into time here, for two reasons worth separating:

- The baseline it is supposed to beat is already good. A growable `List` grows
  amortised O(1) and its realloc is a `memcpy`, which is fast enough that
  avoiding the copy saves less than the page indirection costs.
- Every access pays `pages[id/rows][id%rows]`, and unlike the copy, that cost
  is paid on the hot path rather than amortised over growth.

The advantage regime was then sought rather than assumed, and it exists — on
the MEMORY axis, not the time one. A page can only be handed back once its
whole id range is dead, so the shape of the deaths decides everything:

- **spread death** (every tenth id survives): 90% of entities gone and **not
  one page** released, because every page still holds a live entity. Chunking
  returns nothing.
- **region death** (the low 90% of the id range dies together — a level
  unloaded, a wave cleared, anything that allocated its ids in one run):
  **89% of the footprint comes back** (51,200 cells held against a growable
  column'\''s 480,000, which never shrinks at all).

So the regime is not "many entities died" but "a REGION of the id space
died", and the price is ~1.6-1.9x on the shrink and regrow operations
themselves. `test_backend_parity` gates the release against the failure that
would make the memory number meaningless: neighbouring pages'\'' entities must
be untouched, and a released page must be reusable.

The honest scope of the TIME result: the commercial chunk stores this
mirrors (Unity DOTS, Unreal MassEntity) do not use chunks primarily to avoid
reallocation. They use them because a chunk is an ARCHETYPE-HOMOGENEOUS block,
which makes it a natural unit for SIMD iteration and for handing one chunk per
worker to a job scheduler. This variant reproduces the allocation property but
not the layout property — it pages a dense id-indexed column, not an archetype
block — so it measures the weaker half of the idea. A chunked ARCHETYPE
backend, where a page is a homogeneous component block, remains the version
that could plausibly win, and is not what these rows rule out.

## Concurrency — work stealing vs static fan-out

`parallelize` fixes the split before any task runs, so a round costs as much
as the unluckiest block. `scheduler/workstealing.mojo` starts from the same
split and lets idle workers drain other ranges; a claim is one atomic
`fetch_add`, so every index is still issued exactly once no matter how the
steals interleave (`test_workstealing` gates that, including workers > tasks).
Its cursors are spaced one per cache line — packing them would give back more
than the stealing wins, as the false-sharing table below shows.

The result only means something against a cost distribution, so three are run:

- **uniform** — static partitioning is already optimal, so this prices what
  stealing's atomics COST when there is nothing to rebalance. At 2-4 workers
  it is a dead heat, which is the answer: the mechanism is close to free.
- **skewed** (cost rises with index) — stealing wins **~1.5-2x**, the margin
  growing with worker count because a wider static split gives the unlucky
  worker a proportionally larger share of the tail.
- **spiky** (a few very expensive tasks) — mostly a wash. With 512 tasks and
  16 spikes, static blocks each catch roughly the same number of spikes by
  luck, so there is little imbalance left to fix. Stealing pays off when the
  cost gradient is systematic, not merely when some tasks are expensive.

One result worth separating out: on the UNIFORM workload stealing pulls ahead
again at 8-12 workers. Nothing about the tasks is uneven there — the CORES
are. This is a 6 P-core / 8 E-core part, so once the width forces work onto
E-cores an equal split of tasks is no longer an equal split of wall time, and
the dynamic pool absorbs that while a static one cannot. That is the same
topology effect the scaling curves show as a dip at 8 workers, seen from the
other side.

## Concurrency — false sharing (cache-line contention)

The core-scaling curves showed the solver saturating near 1.5-1.6x and Amdahl
explained most of it. This table answers the rest: is the parallel region
itself paying for coherence traffic? Every row does identical work and yields
identical totals (verified at the end of the run) — only the ADDRESS SPACING
of the per-worker accumulators changes.

With atomic increments the effect is unambiguous: packing accumulators onto
one 64-byte line costs up to **~11x**, and the penalty GROWS with worker count
(~3.5x at 2 workers, ~11x at 12) because every added core joins the ownership
ping-pong. Spacing them one per line removes it completely, and stride 16 buys
nothing over stride 8 — confirming this is a cache-line property, not a
"wider is always better" gradient. Stride 2 is the instructive middle: it is
as bad as stride 1 while the workers still fit on one line, then halves once
it splits them across two.

The `plain` rows are a deliberate NULL RESULT and are the reason this
benchmark uses atomics at all. A non-atomic `p[i] += v` loop shows NO stride
effect whatsoever and runs ~30x faster than the atomic version, because the
compiler keeps the accumulator in a register and writes back once — collapsing
thousands of contended stores into a single one. It measures the optimizer,
not the hardware. `local` (accumulate in a local, store once) costs the same
as `plain`, which confirms the diagnosis and is also the pattern that makes
kernels immune by construction.

Bearing on this engine: the solver's parallel paths write whole bodies and
contact pairs at island/color granularity, not packed per-worker counters, so
there is no such accumulator array to contend over. Taken with the Amdahl
reading above, the 1.5-1.6x ceiling is the SERIAL REMAINDER, not contention —
which is what makes the serial 60% the right thing to attack next.

## Maturity assessment

- **Every comparable-method seam has a benchmark row.** The seam / parity-test /
  benchmark coverage matrix lives in `docs/CATEGORY.md` §2 (architecture law v2,
  2026-07-13): a seam variant ships with its parity test AND its report row.
- **Swappability holds end-to-end.** All five ECS backends (sparse, archetype,
  bitset, reactive, naive) plus the OOP engine produce identical results on the
  shared scenarios (`test_backend_parity`, `test_oop_engine`, `test_system_soa`),
  so the storage seam is mature: strategies swap with zero game-code change.
- **The scheduler seam swaps too.** Sequential, entity-actor and system-actor
  schedulers — under serial and parallel dispatch — all produce identical world
  state (`test_scheduler_parity`, across sparse and archetype backends). The
  benchmark shows the cost shape: the actor schedulers add mailbox build/route/
  drain overhead over the plain loop, and parallel dispatch only starts to repay
  its thread-launch overhead near N=4000 — below that the per-actor work is too
  small to amortize it. Determinism is preserved because each parallel round only
  mutates disjoint data and merges/routes serially.
- **ECS vs OOP is a crossover, not a winner.** The fast SoA/SIMD path is what
  makes ECS competitive — and it wins exactly where theory says it should:
    - W2 scattered selective-read over fat entities: `archetype (soa)` beats
      `oop-fat`, because the hot Position column stays cache-resident while the
      AoS object drags its cold payload through cache on every access.
    - W3 column integrate: `archetype (simd)` is fastest by far — contiguous
      columns vectorize; AoS objects do not.
    - W1 slim full-update (tiny components, touch everything): AoS/OOP stay
      competitive — there is no locality gap to exploit, so the paradigm with
      the least indirection wins.
    - W4 structural churn (add/remove components): `sparse`/`oop` beat
      `archetype`, which pays archetype relocation.
  The earlier 'OOP always wins' result was an artifact of measuring the ECS
  *handle* path on the *one* workload (W1-shaped) where AoS has no disadvantage.
- **Collision scales.** Quadtree/octree, spatial hash and BVH all pull away from
  brute force as N grows (its total time grows quadratically), and narrowphase
  cost ranks cheap→expensive (AABB ≈ circle < SDF < OBB < SAT < GJK+EPA);
  AABB/SAT/OBB/GJK agree on hit counts, confirming they detect the same overlaps.
- **The N ceiling is gone (was: `InlineArray[Int, cap]` by value).** The sparse
  index no longer has a fixed cap — `test_sparse_large` spawns **1,000,000**
  entities and checks counts and high-id component reads. The remaining
  `InlineArray` in `ecs/archetype.mojo` indexes archetype-graph edges by
  *component slot*, not by entity, so it does not bound N.
  What the tables above still under-show is the RAM-spill REGIME: the movement
  rows stop at N=65536, where a fat entity still reaches L3, so the W2 locality
  win reads as ~2x-4x. The memory-mountain probe in
  `ECS_VS_OOP_INVESTIGATION.md` §3 carries the workload past L3 (up to 4,194,304
  elements / 64 MB) and the gap widens as predicted — fat selective read goes
  SoA 0.44 vs AoS 1.82 ns/op (**4.1x**, still widening with N).
- **Hardware profiling backs the locality claim (four-way cross-validation).**
  The layout argument is not left as theory — `ECS_VS_OOP_INVESTIGATION.md` §5
  pins it with four independent instruments that agree:
    - `llvm-mca` (static): the AoS and SoA fat loops are IDENTICAL
      (4009 cycles / 1000 iter, IPC 1.00) — so arithmetic is not the difference.
    - `cachegrind` (deterministic, no prefetcher model): AoS fat read misses L1
      **100%** and last-level **83.8%**; SoA misses 12.5% / 0.5%. This is the
      no-prefetch upper bound.
    - `perf stat` (real PMCs, `paranoid=-1`, pinned to a P-core, N=65536x400):
      AoS sequential IPC 0.94 / L1-dcache miss 17.4% (**5.6x** slower than SoA);
      AoS SCATTERED — which defeats the stride prefetcher — falls to IPC 0.64 /
      30.9% miss (**8.3x**). SoA is nearly immune to scatter (0.026 -> 0.0275 s,
      +6%) because the 512 KB position column stays L2-resident.
    - the timing memory-mountain above.
  Alder Lake's stride prefetcher is what reconciles cachegrind's 84% predicted
  RAM misses with the measured 5.6x: it hides most of them while the access
  pattern stays linear, and stops helping the moment it does not.

_Conclusion: LudensEngine's seams are proven correct, and once ECS is measured
through its intended SoA/SIMD path it lands where its data-locality profile
predicts — beating OOP on selective/columnar/SIMD workloads while OOP stays
ahead on tiny touch-everything updates and structural churn._
