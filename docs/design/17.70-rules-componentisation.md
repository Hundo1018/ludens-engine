# 17.70 — rule framework: componentisation and OOP comparison

Question (2026-10-27): the rule framework (`gameplay/rules.mojo`, `gameplay/abilities.mojo`,
`gameplay/hit_pipeline.mojo`) is built and gated. Two items stay open in the roadmap entry:
(a) the runtime / ECS componentisation, and (b) the comparison against the `oop` package.

## Current state (verified against source)

| piece | where | storage |
|---|---|---|
| attributes (fixed point 1/1000, add / mul / override) | `gameplay/rules.mojo:125` `Attributes` | plain struct fields |
| tags (hierarchy, ≤ 64) | `gameplay/rules.mojo:64` `TagRegistry` | bitmask in `Actor` |
| effect instances | `gameplay/rules.mojo:116` `EffectInst` | `List` inside `Actor` |
| actor | `gameplay/rules.mojo:254` `Actor` | one struct holding all of the above |
| serialization | `gameplay/rules.mojo:394` `actor_to_bytes` / `:430` `actor_from_bytes` | byte list |

So the framework keeps each actor as one value. It does not use `ecs/`. The `ecs` package has three
storage backends that already sit behind one `StorageBackend` seam (`ecs/archetype.mojo:150`,
`ecs/bitset_backend.mojo:33`, `ecs/chunked_backend.mojo:117`).

## (a) Componentisation: the question to answer by measurement

Is the per-actor struct (AoS) or per-component columns (SoA through `ecs`) faster for the access
pattern the rules use? The access pattern is: read one attribute for many actors (the damage pipeline
and the ability check), with a small subset of actors changing per tick. `bench_rules` already measures
this for the struct layout: at 1000 actors, 4 attributes, 10 % changing per tick, a read costs
17 / 29 / 137 ns on the dirty cache (K = 4 / 16 / 64).

The componentised version would store `Attributes` as an `ecs` component and `EffectInst` as a
second component keyed by the same entity. It is a candidate only if the same bench, same workload,
measures it on the same host. No numbers exist for it yet, so no claim is made here.

Rule for this item: the seam (`StorageBackend`) must be kept, and parity must hold. A componentised
`Rules` must give the same damage totals and the same effect expiry tick as the struct version on the
20000-step sequence used by `tests/test_rules.mojo`.

## (b) OOP comparison

`oop/engine.mojo` is the comparison baseline package (layer 6, benchmark only). The planned comparison
is one workload run through both: 1000 actors, buffs with timed expiry, damage with resistance and a
shield. Measured: ns per tick, and whether the final actor states match (byte equality for the
struct version, field equality for the OOP version). The bench reports both. Advantage is not assumed:
the roadmap says to measure first.

## (b) Result: parity (2026-10-27)

`oop/rules_oop.mojo` implements the duration-buff and periodic-damage subset as objects that own
their effects (`OopCharacter.advance`, `OopCharacter.speed`). `tests/test_rules_oop.mojo` 4/4 runs
500 actors through the same workload in both: +20 % speed for 300 ticks, 10 damage per 30 ticks for
300 ticks, 400 ticks total. Speed at tick 150 is 6000 and at tick 301 is 5000 (fixed point) in both,
for every actor; health ends at 0 and dead in both; 0 mismatched fields. The subset excludes tags,
stacking modes, resistance and shields, so parity covers only that subset.

## (b) Result: timing (2026-10-27)

`benchmarks/bench_rules_oop.mojo` times only the 400-tick loop, same subset, ns per actor-tick
(four runs, each run alternating the two variants; report rows in `BENCHMARK_REPORT.md`):

| N | rules (value struct) ns | oop (object) ns | runs |
|---:|---|---|---:|
| 1000 | 10.1 – 16.3 | 10.9 – 20.8 | 4 |
| 10000 | 17.8 – 25.1 | 11.5 – 14.1 | 4 |

At N = 1000 the ranges overlap. At N = 10000 `rules` is slower in all four runs, by about 1.3 to 2
times. Diagnosis below; no claim is made here that either layout is faster.

### Diagnosis of the N = 10000 gap (`scripts/rules_icount.py`, probe `benchmarks/probes/rules_oop_probe.mojo`)

Predictions were written in the probe header before the runs (P1 to P4). Cost is per actor-tick,
the tick loop only (TICKS = 400 run minus TICKS = 0 run).

| check | measured | result |
|---|---|---|
| P1: Ir per actor-tick within 1.5x | rules 87–89, OOP 113–114 | holds (rules does fewer instructions) |
| P2: D1 read misses ≥ 2x OOP at N = 10000 | rules 2.3, OOP 1.7, flat in N | fails (1.36x) |
| P3: at N = 1000, D1 ratio < 2x | 1.36x | holds |
| P4a: rules LL misses at N = 10000 ≥ 3x its N = 1000 value (LL forced to 1 MiB) | 2.08 vs 0.03 | holds |
| P4b: rules LL misses ≥ 2x OOP at N = 10000 | 2.08 vs 1.50 | fails (1.39x) |

Wall-clock sweep (ns per actor-tick, minimum of 5 process runs, TICKS 400 minus TICKS 0):

| N | 1000 | 2000 | 5000 | 10000 | 20000 |
|---|---:|---:|---:|---:|---:|
| rules | 9.6 | 11.5 | 23.1 | 17.9 | 22.7 |
| oop | 9.9 | 14.4 | 11.0 | 12.4 | 11.7 |

LL misses per actor-tick with the last-level cache forced to 1 MiB: rules 0.03 / 0.06 / 0.79 / 2.08 at
N = 1000 / 2000 / 5000 / 10000; OOP 0.00 / 0.02 / 0.00 / 1.50.

Reading: instruction count does not explain the gap (rules does fewer instructions at every N). The
gap onsets where rules starts missing the 1 MiB level (between N = 2000 and 5000), and OOP starts
missing at N = 10000. That fits a footprint explanation. It is not proven: the 1 MiB level is a
simulation, not the host's L2 measured, and the per-actor size (about 3 MB rules against 0.6 MB OOP) is
an estimate that was not measured. The N = 2000 OOP value (14.4 ns) is a single outlier, not
investigated.

The label changed in this note: both variants are array-of-structs (rules keeps a per-actor `List` of
effects; OOP keeps a per-object `List`), so the SoA question stays with item (a).

Host provenance: the cached report rows were measured on a 2.10 GHz host; the header of the
regenerated report reads 2.80 GHz. Rows from the two hosts are not comparable across the report.

## Status

(a) componentised variant on `ecs/`: not implemented. (b) parity: done. (b) timing: measured as
above, at N = 1000 to 20000 on one workload. The N ≥ 5000 gap tracks the onset of last-level misses
(footprint reading, not proven); instruction count does not explain it.
