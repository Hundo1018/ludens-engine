# 17.14 導航:navmesh、尋路 seam、動態挖洞

## 問題

引擎沒有任何導航能力。ROADMAP 17.14 要求 navmesh bake、A* / funnel、動態障礙挖洞、off-mesh link、
crowd 避讓,以及流場、3D 體積導航、階層式尋路。本筆記涵蓋全部:bake、尋路 seam、流場、挖洞、
off-mesh、crowd 避讓、3D 體積導航、HPA*。

## 放在哪一層

新套件 `nav`,layer 3。它只需要 `geometry`(向量;crowd 的鄰居查詢用自帶的均勻格,不用 `spatial` 的雜湊格,因為後者的 `insert` 會 raise,而內層迴圈不 raise);
不 import `collision` / `physics`:烘焙輸入是呼叫端傳入的三角形,動態障礙是 AABB。
與物理地面的一致性由 `tests/test_nav_world.mojo`(integration tier)在測試層驗證,而不是讓 `nav`
依賴 `physics`。17.15 AI 會在 `gameplay`(layer 5)同時使用 `nav` 與 `collision` 的世界查詢。

## Bake 管線

| 步驟 | 對照 Recast | 本實作 |
|---|---|---|
| 體素化 | `rcRasterizeTriangles`(逐格裁切三角形) | 相同;另外排除只碰到格線邊界的零寬切片(兩片相鄰地板在格線上接縫時,Recast 會多出一列 span) |
| 過濾 | low-hanging / ledge / low-height | low-hanging 與 low-height;ledge 由侵蝕吸收(落差 > climb 的鄰居不連通 → 邊界 → 被侵蝕) |
| 緊湊化 | `rcBuildCompactHeightfield` | 相同(4 鄰接、climb 與淨高條件) |
| 侵蝕 | `rcErodeWalkableArea`(2/3 chamfer) | 相同,另有視窗版 `erode_window`(挖洞用) |
| 區域 / 輪廓 / 多邊形 | watershed → contour → triangulate | **每 tile 貪婪矩形合併**;多邊形是 XZ 對齊矩形(凸),不跨 tile |

矩形合併的代價是多邊形數(斜牆變成階梯),好處是 tile 可單獨重建且沒有輪廓簡化的誤差參數。
高度不取矩形角點(矩形允許 `max_climb` 以內的地板差,跨坡折時非平面),而是取點下方 span 的地板
加中央差分坡度(`NavMesh.height_at`)。

## 尋路 seam

`trait PathFinder`:`PolyFunnel`(多邊形 A*,節點位置 = 進入 portal 中點,Detour 的成本模型;
simple stupid funnel;預設再做一次可見性平滑)、`GridAStar`(8 連通 span,不切角)、
`FlowFieldPath`(每目標一張 Dijkstra 積分場,依 `mesh.version` 快取)。

Parity 定律(`test_nav_parity`):可達性相同;每段行走線段通過 `NavMesh.raycast`(Amanatides–Woo 精確
走格,沿著連通關係走,所以不會跳層);`GridAStar` 與 `FlowFieldPath` 長度相同(同一圖上的兩個精確
最短路)。funnel 與 octile 長度的界是**經驗界**,不是定理:多邊形 A* 的走廊不保證是最短走廊,
octile 路徑在每個轉角需要額外格子。

## 動態障礙

`add_obstacle` / `remove_obstacle` 只登記,`update` 才套用:在變動視窗(障礙 AABB ⊕ (r+1) 格)內重算
`blocked`、在同一視窗內重算侵蝕、重建視窗觸及的 tile、重建連結。視窗侵蝕的正確性:chamfer 最短路是
單調的,留在兩端點的包圍盒內;距離 < 2r 必來自 r 格內的邊界,因此在「寫入窗 ⊕ (r+1)」的計算窗內是精確
的,較大的距離只可能被高估,不改變旗標。測試以「增量 == `rebuild_all`」逐位比對驗證。

## Crowd 與避讓 seam

`Crowd[A: Avoidance]`:均勻格鄰居查詢(counting sort,無雜湊、不 raise)→ 偏好速度(往下一個 path corner;
右手偏置 5 % 打破完全對稱的對峙)→ 避讓變體 → `NavMesh.move_along`(逐格走、沿被擋的格邊滑動,
Detour `moveAlongSurface` 的體素版)→ corner 推進。corner 以可見性推進(下一個 corner 可直線到達就跳過),
目前 corner 看不見(被推出走廊)就重新規劃,每個 agent 至少間隔 `replan_cooldown` tick。

變體:`Orca`(RVO2 的半平面構造與 `linearProgram1/2/3` 逐行移植)、`SampledRvo`(取樣 + 互惠 VO 的
碰撞時間懲罰)、`SocialForce`(Helbing)。重疊 agent(距離 0)以 index 推導的方向分開,不產生 NaN。

量測到的失敗模式與對策(都在 `test_crowd` 留下案例):
- 16 agent 對心交換在中心形成緩慢旋轉的環 → 右手偏置(所有 agent 同向偏)讓環變成會排空的渦流。
- 取樣 RVO 加入零速度候選 → 停下比繞行便宜,走廊與單門場景整體凍結 → 不加零速度,改提高碰撞時間權重。
- 單門瓶頸中被推過 corner 的 agent 回頭找 corner,堵住門 → 可見性推進 + 看不見時重新規劃。
- 軸向回退式牆滑在 corner 卡死 → 逐格 `move_along`。

ORCA 的無碰撞保證在牆邊不成立:LP 之後的 navmesh 滑動改變了速度,鄰居各負擔一半的假設不再成立
(門口量到 0.03 m = 10 % 半徑)。加入 navmesh 邊界作為 ORCA 靜態障礙線可修,列為剩餘。

## 3D 體積導航

佔據格沿用 navmesh 的逐格裁切光柵器(立方體素),依半徑做可分離盒膨脹(盒包含球,保守)。八叉樹在
補成 2 的冪的立方體上建,節點是否均勻由 summed-volume table O(1) 判斷(格外視為阻擋)。自由葉是圖節點,
相鄰 = 共享部分面。`SvoAStar` 起初用葉中心當節點位置,大葉讓距離失真,實測把一條路線送到建築的另一側
(長 26 m vs 稠密 22 m);改用 portal 成本模型(節點位置 = 進入的共享面片中心)後與稠密 A* 一致。
連續兩個 portal 落在同一個凸葉的面上,所以原始路線本身就合法,平滑只是縮短。

## 階層式尋路

cluster = navmesh tile。portal 圖的節點是 portal 中點與 off-mesh 端點,同一凸多邊形上的兩點以直線相連
(線段在該多邊形內),所以 tile 內的連通性與 portal 圖相同,階層搜尋的可達性是精確的。抽象邊 = 每個
entrance 在其 tile 內一次 Dijkstra。最後以粗路徑經過的 tile 為遮罩跑 `PolyFunnel`,所以長度界與平面搜尋
相同。量測:128 m 迷宮上並不比平面搜尋快(起終點接到 tile 的成本與省下的相當),好處是只細搜粗路徑上的
tile —— 串流世界中未載入的 cell 只需要保存 entrance 間的成本。

## 已知限制

- 連結重建是全域的(與多邊形數成線性);64 m 迷宮上 incremental update 1.2 ms,其中大部分是這一步。
- 多邊形數高於 Recast(無輪廓簡化);bench 報告多邊形數。
- `find_span` 的垂直容差是 `agent_height`;多層場景中查詢點應接近要找的那一層地板。
