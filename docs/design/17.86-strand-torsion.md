# 17.86 — strand torsion integration

Question (2026-10-27): can `StrandSet` / `Rope` and `CosseratRod` share one torsion model, so a
strand can twist, store that twist, and hand it to a fluid or contact coupling?

## Finding: the gap is in the state, not in the solver

| type | state per particle / segment | twist DOF | evidence |
|---|---|---|---|
| `CosseratRod` | position `x`, segment quaternion `q`, angular velocity `omega` | yes: `twist_angle(j)` from the Darboux vector | `physics/cosserat_rod.mojo:52-63`, `:137-145` |
| `StrandSet` | position `x`, velocity `v`; direction projection, no frame | no | `physics/strand.mojo:69-87`; `:41-43` states "no twist" in the model |
| `Rope` | position `x`, `prev`, `v`; XPBD distance constraints | no | `physics/rope.mojo:32-47` |

So "integrating" `StrandSet` with `CosseratRod` cannot be a call that passes twist across: a `StrandSet`
strand has no frame to carry a twist angle. Building a `CosseratRod` from a strand's particles gives
frames from the chords, and a planar strand's twist is zero by construction.

## Decision

Add one optional per-particle state to `StrandSet`: a material twist angle `twist[i]` (rad, about the
local chord), default 0, plus a torsional compliance. The bending update already projects onto the
chord; the twist update is a separate XPBD constraint on the angle between adjacent material frames,
matching `CosseratRod._bend_twist`. With the default compliance infinite, `StrandSet` behaves as it
does now, so existing golden sections should not change. (Verify with the gate, not by argument.)

Rejected alternative: make `Rope` a `CosseratRod` wrapper. That would change `Rope`'s public
behaviour (tie, attach, quarantine) and its serialization in one step. Keep the three types and add
the adapter only where a coupling needs twist.

## Interface (planned)

- `StrandSet.twist: List[Real]` per particle, `StrandSet.torsion: Real` (compliance, 0 = infinitely
  stiff, default `inf` = off).
- `StrandSet.write_state` / `read_state` (`physics/strand_ext.mojo:36-43`) gain the `twist` list.
  Old snapshots without it read as zero (version bump, not silent).
- `rod_from_strand(s: StrandSet, strand: Int, mass: Real) raises -> CosseratRod`: copies the strand's
  particles into a rod so the two solvers can be compared on the same configuration.

## Parity test (planned, `tests/test_strand_torsion.mojo`)

Same twisted strand (one end pinned, the other turned by φ) in `StrandSet` and in `CosseratRod`:
after settling, the twist angle profile must agree within a stated tolerance. Predictions are to be
written in the header before the run. Also: `torsion = inf` reproduces the current `StrandSet` output
bit for bit (regression guard).

## Status

Not implemented in this commit. The steps are (a) the state field and serialization, (b) the twist
constraint, (c) the parity test, (d) the golden update. Item (2) of the roadmap entry (plectoneme
measurement) is already done on `CosseratRod` alone (`tests/test_rod_plectoneme.mojo`, `tests/test_rod_greenhill.mojo`);
its constants are recorded as unvalidated against the analytic form.

Item (3), fluid and contact coupling, needs its own note: the strand's radius and the `StrandCapsule`
contact (`physics/strand_ext.mojo:52` `strands_collide`) would have to carry the torsional frame to the
contact normal. That is not designed here.
